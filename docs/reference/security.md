# Security

Skrib is designed with a security-first approach: passwordless authentication, zero-knowledge encryption, and controlled access at every layer.

## Authentication

### WebAuthn / Passkeys

Skrib uses WebAuthn Level 2 with discoverable (resident) credentials. No passwords are used anywhere in the system.

**Registration flow:**

1. User submits a username (4-15 chars, alphanumeric + underscore, reserved words blocked)
2. Server creates a registration challenge
3. User enrolls a platform passkey with `navigator.credentials.create()`:
   - `authenticatorAttachment: "platform"` — uses built-in biometrics (Touch ID, Windows Hello, etc.)
   - `residentKey: "required"` — credential stored on the authenticator for usernameless login
   - PRF extension requested for automatic key recovery
4. Server verifies the credential and stores the public key
5. E2E key pair generated client-side and wrapped for portability (see [E2E Encryption](end-to-end-encryption.md))

**Login flow (usernameless):**

1. `GET /api/auth/login/begin` returns a challenge with no `allowCredentials` — the authenticator picks the credential
2. User authenticates with biometrics
3. `POST /api/auth/login/complete` with credential ID — server identifies the user by credential
4. Client-side key recovery runs (PRF automatic, passphrase fallback)

### Session Tokens

- Format: base64-encoded `username:random_hex_string`
- Passed via `Authorization: Bearer {token}` header (HTTP) or `?token={token}` query param (WebSocket)
- Validated by decoding and checking the username exists with `active` status
- Stored in `localStorage` on the client

## Registration Modes

Controlled via admin panel or `SKRIB_REGISTRATION_MODE` environment variable:

| Mode | Description |
|---|---|
| `open` | Anyone can register and immediately access the app |
| `approval_required` | User registers and receives an approval code; admin must approve before access |
| `invite_only` | Registration requires an invite token generated by an admin |
| `closed` | No new registrations allowed |

The first registered user is automatically approved and given the `admin` role.

### Invite System

Admins create invite tokens via `POST /api/server/invites`. Invite links include the token as a query parameter. Tokens are single-use.

## Authorization

### Global Roles

| Role | Capabilities |
|---|---|
| `admin` | Full access: server settings, user management, plugin management, all room operations |
| `moderator` | User approval, kick users from rooms, manage room folders |
| `user` | Join rooms, send messages, create rooms |

### Room Roles

| Role | Capabilities |
|---|---|
| `owner` | Full room control: settings, topic, kick, delete, manage members, approve/deny join requests |
| `op` | Manage members, set topic, kick, approve/deny join requests |
| `voice` | Standard participation (reserved for future permission tiers) |
| `member` | Read and send messages |

Permission checks are centralized in `backend/skrib/permissions.py`:

- `check_room_access(username, room_id)` — verify membership
- `require_room_op_or_global_mod(username, room_id)` — room op, owner, or global admin/mod
- `can_edit_resource(username, resource_owner, room_id)` — author or privileged role

## Security Boundaries

### Server-Side

- **Zero-knowledge**: Message content is encrypted client-side. The server stores ciphertext only.
- **Header stripping**: The `PluginAuthMiddleware` strips all client-supplied `x-skrib-*` headers before injecting authenticated values, preventing header spoofing.
- **Path traversal protection**: Plugin file serving validates paths to prevent directory traversal attacks.
- **GZip compression**: Enabled via middleware for all responses.
- **CORS**: Configured via `CORS_ORIGINS` (defaults to `["*"]` — should be restricted in production).
- **Foreign keys enforced**: SQLite foreign key constraints enabled on every connection.

### Client-Side

- **Private key isolation**: RSA private keys stored in IndexedDB, never transmitted in plaintext.
- **Key wrapping**: Private keys are only transmitted in encrypted (wrapped) form for cross-device portability.
- **No plaintext in transport**: Messages are encrypted before being sent over WebSocket or HTTP.
- **XSS mitigation**: All user-generated content is HTML-escaped via `escapeHtml()` before DOM insertion.

### Plugin Sandboxing

- **Manifest permissions**: Plugins declare required permissions; the bus enforces them at runtime.
- **Namespace isolation**: Plugin WebSocket events are auto-prefixed, preventing namespace collisions.
- **Isolated storage**: Each plugin has its own SQLite database, no access to core tables.
- **Auth middleware**: Plugin HTTP routes go through dedicated authentication that injects trusted headers.

## WebSocket Authentication

`WS /api/ws?token={sessionToken}`. The server validates the token exactly as it
validates an HTTP bearer token. An invalid token closes the connection with code
`1008`.

## Server-Side Storage

The server stores encrypted key material but **never** holds:

- user private keys (only wrapped blobs),
- room key plaintext (only RSA-encrypted per-user blobs),
- message plaintext (only AES-GCM ciphertext).

### Users table — security-relevant columns

| Column | Purpose |
|---|---|
| `credential_id` | WebAuthn credential identifier |
| `public_key` | WebAuthn credential public key, for signature verification |
| `encryption_public_key` | RSA-OAEP public key JWK, for encrypting room keys to this user |
| `encrypted_private_key` | PRF-wrapped private key backup |
| `passphrase_encrypted_private_key` | Passphrase-wrapped private key backup |

### Challenges table

WebAuthn challenges are single-use. Each is stored with its type (`registration`
or `login`) and a timestamp, then deleted after verification.

## Threat Model

| Threat | Mitigation |
|---|---|
| Password theft/phishing | No passwords — WebAuthn passkeys only |
| Server compromise reading messages | Zero-knowledge — server stores only ciphertext |
| Session hijacking | Random hex tokens, HTTPS in production |
| Rogue plugin accessing core data | Manifest permissions, namespace enforcement, isolated storage |
| Header spoofing to plugin routes | PluginAuthMiddleware strips client `x-skrib-*` headers |
| Unauthorized registration | Registration modes (closed/invite/approval), admin controls |
| Unauthorized room access via join requests | Join requests only for public rooms; approval required by room ops/owners/admins |
| Lost device | PRF-based automatic key recovery, passphrase manual fallback |
| XSS via message content | Messages decrypted and HTML-escaped before rendering |

### Residual risks, stated plainly

- **Server compromise.** An attacker with server access sees only ciphertext and
  wrapped key blobs. Passphrase-wrapped keys are protected by PBKDF2 at 600 K
  iterations.
- **Weak passphrase.** The passphrase-wrapped blob lives on the server, so a
  server-side attacker can attempt offline brute force. 600 K iterations make this
  expensive but not impossible against a weak passphrase. This is one reason
  user-invented passphrases are being removed in favour of generated phrases and
  PRF — see `docs/spec/2026-08-02-onboarding-invite-links.md` §4.
- **Domain changes.** Changing origin (a different subdomain, say) makes IndexedDB
  and PRF recovery unavailable. Passphrase recovery is the bridge.
- **Lost authenticator.** WebAuthn is the only auth method, so losing the
  authenticator means losing login. The passphrase alone is not sufficient — it
  recovers the *encryption* key only after a successful WebAuthn assertion.
- **CORS** defaults to permissive (`*`) for development and must be restricted in
  production.
