# End-to-End Encryption

Skrib implements zero-knowledge E2E encryption where the server never sees plaintext message content. All cryptographic operations happen client-side using the Web Crypto API.

## Cryptographic Primitives

| Purpose | Algorithm | Key Size |
|---|---|---|
| User key pair | RSA-OAEP (SHA-256) | 2048-bit |
| Room symmetric key | AES-GCM | 256-bit |
| Message encryption | AES-GCM | 256-bit (room key) |
| Message IV | Random | 96-bit (12 bytes) |
| PRF key wrapping | AES-GCM via HKDF | 256-bit |
| Passphrase key wrapping | AES-GCM via PBKDF2 | 256-bit |

## Key Hierarchy

```
User RSA-OAEP Key Pair (per user)
  └── Private key stored in IndexedDB, public key on server
  └── Used to encrypt/decrypt room keys

Room AES-GCM Key (per room, per epoch)
  └── Generated by room creator or on key rotation
  └── Encrypted individually for each room member using their RSA public key
  └── Stored on server as encrypted blobs in room_keys table

Message Encryption
  └── Each message encrypted with the room's current-epoch AES-GCM key
  └── Random 12-byte IV per message
```

## Key Generation

### User Key Pair

Generated during passkey enrollment (`enroll-passkey.js`):

1. `crypto.subtle.generateKey()` creates an RSA-OAEP 2048-bit key pair
2. Public key exported as SPKI and sent to the server
3. Private key stored locally in IndexedDB
4. Private key wrapped for portability (see Key Portability below)

### Room Key

Generated when a room is created or when a key epoch rotates:

1. `crypto.subtle.generateKey()` creates an AES-GCM 256-bit key
2. Key exported as raw bytes
3. For each room member: encrypt the raw key with the member's RSA-OAEP public key
4. Upload all encrypted blobs to `POST /rooms/{room_id}/keys`

## Message Encryption Format

Encrypted messages are stored as JSON envelopes:

```json
{
  "v": 1,
  "epoch": 3,
  "iv": "<base64-encoded 12-byte IV>",
  "ct": "<base64-encoded ciphertext>"
}
```

| Field | Description |
|---|---|
| `v` | Envelope version (currently `1`) |
| `epoch` | Room key epoch used for encryption |
| `iv` | Random initialization vector (base64) |
| `ct` | AES-GCM ciphertext of the plaintext message (base64) |

Messages in the database have `content_type: "encrypted"` and `key_epoch` fields.

## Key Distribution

When a user is invited to a room (via `/invite` command or Add Member modal):

1. Inviter fetches the invitee's RSA public key from `GET /users/{username}/public-key`
2. Inviter fetches all current room key epochs
3. For each epoch: encrypt the raw AES-GCM key with the invitee's RSA-OAEP public key
4. Upload all encrypted keys to `POST /rooms/{room_id}/keys`
5. Invitee can now decrypt all historical messages in the room

## Key Epoch Rotation

Room keys use an epoch-based rotation system:

- Each room can have multiple key epochs (epoch 0, 1, 2, ...)
- New messages are encrypted with the latest epoch
- Older messages can still be decrypted using their recorded epoch
- A new epoch is created when members change or when security requires rotation

### Auto-Regeneration

If a user's key pair was regenerated (lost device, no recovery available):

1. On room load, the client attempts to decrypt room keys for all epochs
2. If all epochs fail to decrypt, the client detects a key pair mismatch
3. A new key epoch is generated and encrypted for all current room members
4. A warning banner is shown: older messages encrypted with prior epochs are unreadable

## Key Portability

Private keys need to travel between devices. Skrib supports two wrapping methods:

### PRF Wrapping (Automatic)

Uses the WebAuthn PRF (Pseudo-Random Function) extension:

1. During passkey enrollment, the PRF extension output is requested with a fixed salt (`skrib-encryption-key`)
2. The PRF output is fed through HKDF (SHA-256) to derive a 256-bit AES-GCM wrapping key
3. The RSA private key is wrapped (encrypted) with this derived key
4. The wrapped blob is stored on the server as `encrypted_private_key`

On login from a new device:

1. WebAuthn assertion includes PRF output (same salt)
2. Same HKDF derivation produces the same wrapping key
3. Private key is unwrapped automatically — no user interaction required

### Passphrase Wrapping (Manual Fallback)

For authenticators without PRF support:

1. During registration, user provides a recovery passphrase (minimum 32 characters, must include uppercase, lowercase, number, and special character)
2. Passphrase is processed through PBKDF2 (600,000 iterations, SHA-256) to derive a 256-bit AES-GCM wrapping key
3. The RSA private key is wrapped with this derived key
4. The wrapped blob is stored on the server as `passphrase_encrypted_private_key`

On login from a new device without PRF:

1. User is redirected to the key recovery page
2. User enters their passphrase
3. Same PBKDF2 derivation produces the same wrapping key
4. Private key is unwrapped

### Recovery Priority

On login, the client resolves the private key with this priority:

1. **Local key exists** in IndexedDB — use it directly
2. **PRF available** and `encrypted_private_key` exists on server — unwrap automatically
3. **Passphrase recovery** — redirect to `/key-recovery.html` for manual entry
4. **No recovery possible** — generate a fresh key pair, warn that old messages are unreadable

## Implementation Files

| File | Role |
|---|---|
| `frontend/src/crypto.js` | All cryptographic operations (generate, encrypt, decrypt, wrap, unwrap) |
| `frontend/src/enroll-passkey.js` | Key pair generation during registration |
| `frontend/src/login.js` | PRF recovery and backup upload on login |
| `frontend/src/key-recovery.js` | Passphrase-based recovery page |
| `frontend/src/app.js` (lines 586-781) | Room key management, epoch rotation, auto-regeneration |
| `backend/skrib/auth/routes.py` | Server-side storage of public keys and wrapped private keys |
| `backend/skrib/rooms/routes.py` | Room key CRUD endpoints |

## Database Tables

**room_keys**: `room_id + key_epoch + username` (composite PK), `encrypted_key` (RSA-encrypted room key blob)

**users**: `encryption_public_key` (SPKI-encoded RSA public key), `encrypted_private_key` (PRF-wrapped), `passphrase_encrypted_private_key` (passphrase-wrapped)

## Security Properties

- The server never sees plaintext messages or raw room keys
- Private keys are only stored locally (IndexedDB) or in wrapped (encrypted) form on the server
- Room keys are individually encrypted per member — removing a member doesn't require re-encryption of history, but new messages should use a new epoch
- The passphrase is never sent to the server — wrapping happens entirely client-side
- PRF wrapping is deterministic per authenticator + salt, enabling automatic cross-device recovery
